# Decisions and their reasons

The original spec is `docs/build-spec-v1.pdf`. It left some things undefined and contradicted itself in places, and the owner delegated those choices ("every undefined thing is up to you"). This file records each choice that is not obvious from the code, why it was made, and what was measured.

Measurements were taken on the first development machine: ffmpeg 4.4.2 (Ubuntu 22.04), Node 24, Python 3.10, faster-whisper 1.2.1, CPU only.

On a different ffmpeg version, `npm test` re-checks size, frame rate, length, picture-and-sound sync and the silent end-card tail. It does not re-check where text lands on screen: the pixel positions quoted below were measured by hand from rendered frames, so look at a frame again if the renderer changes.

## Stack

- **Node.js with a small Python script.** Python alone would have been simpler, since faster-whisper is a Python library. The owner is a JavaScript developer and wants to take part in development, so everything except `scripts/transcribe.py` is JavaScript.
- **Node 22.12 or later**, not 20 as in the spec. `commander` 15 and `vitest` 5 require it.
- **`child_process` through `src/run.js`**, not `execa`. One small wrapper was enough.
- **On Windows the tool runs inside WSL 2, not natively** (2026-11-20, when the owner asked for a Windows install guide). Nothing has been run on Windows, and the code has Linux-only spots: the path `.venv/bin/python`, the `python3` command, a symbolic link to the fonts folder on every render, and programs started without a shell. WSL with Ubuntu 22.04 gives the same Ubuntu, the same ffmpeg 4.4.2 and the same Python 3.10 the project was built and measured on, so the guide (`docs/install-windows.md`) installs that and changes no code. Its Ubuntu steps were run from a fresh copy cloned from GitHub on Ubuntu 22.04.5 (358 tests passed, a first clip cut, the dashboard served); installing WSL itself and the Windows side were written from Microsoft's documentation, since no Windows machine was at hand.
- **`npm audit` is clean** as of 2026-11-19. Earlier it reported high-severity findings in `picomatch`, inside `vitest`'s development-only dependencies, with a downgrade of `vitest` as the only offered fix; that was left alone, and a later install resolved it.

## Rendering

- **Frame rate is converted with the `fps` filter, never with `-r 30`.** The spec's recipes use `-r 30`. On a 60 fps source it put the picture two frames (67 ms) behind the sound; with `fps=30` at the start of the graph, picture and sound match to within one frame. That was measured by hand on 24, 25, 30, 59.94 and 60 fps sources, including an MKV with B-frames; the test suite covers the 60 fps case.
- **`-ss` and `-t` are both input options**, for the render and for the audio extract. With `-t` only on the output and an end card, the source kept playing under the card and its sound was heard in the tail. A test cuts a range that ends just before a beep and requires the clip to be silent.
- **Only the first audio track is used** (`-map 0:a:0?`), for the clip and for the transcriber. The spec's `-map 0:a?` copied every track of a multi-track recording into the clip.
- **ffmpeg runs inside the clip's `work/` folder** and the filter graph refers to `captions.ass` and `fonts` by bare name. A path with a quote, comma or bracket in it broke the `subtitles` filter. `fonts` is a temporary symbolic link to `assets/fonts`, removed after the render.
- **The clip is written to `clip.partial.mp4` and renamed.** A failed re-render leaves the previous `clip.mp4` intact.
- **`--trim` was added** (not in the spec). The owner's source recording has a rounded, coloured border baked into the frame, and 14 pixels removes it. It is capped at 5% of the shorter side so it stays a border remover and does not become a way to crop out logos, which the spec's guardrail forbids.
- **`--crop-x` is the left edge of the crop in source pixels**, clamped to the frame. The spec did not say what the offset was measured from.
- **`--crop-width` was added** (not in the spec), and "Show more of the picture" in the dashboard. On a 16:9 recording of a streamer the 9:16 column is 606 of 1920 pixels wide, and the streamer's face left it whenever they leaned. The crop can be made wider, up to the whole width; it is then shown whole over a blurred copy of itself, the same way the `blur` layout shows the whole frame. It is one fixed window for the whole clip: it does not follow anyone. A crop that follows a face would need a face detector to be installed, and was not built. A width at or below the column gives the plain column and the same filter graph as before, so clips made earlier render the same. A wider crop still fails a brief's `keepFullFrame`, which only the `blur` layout passes.
- **The watermark guardrail was reworded** to "no feature whose purpose is removing marks". As written in the spec it contradicted the `center` layout, which discards about two thirds of the frame width.

- **Quality check, 2026-11-19.** The owner felt the outputs looked poor. Each output was compared frame by frame with the same picture made without compression loss: a part against its source scored SSIM 0.997 and 48.7 dB, a centre clip 0.996 and 48.7 dB, a compilation segment straight from the source 0.997 and 51.6 dB, and one made from a part (encoded twice) 0.995 and 49.0 dB. So the encoding settings (`crf 18`) are not the cause. The causes found: the test source is 1280×720 at about 1.5 Mbps of video and 48 kbps of sound, already soft before the tool touches it; the centre layout enlarges a 404-pixel column 2.7 times and a compilation enlarges 720p 1.5 times; and 60 fps sources lose half their frames at 30 fps. A sharper scaler (lanczos) and added sharpening were tried on one frame and made no visible difference, so neither was adopted.

## Captions and on-screen text

- **Font: Liberation Sans Bold**, from the `liberation2` package, under the SIL Open Font License (text in `assets/licenses`). The spec's style names Arial, which is not installed on Linux, and the subtitle renderer silently substitutes whatever it finds. The render aborts if the bundled font file is missing.
- **Hook top margin is 240.** The hook's white box reaches 18 px above its text. At the spec's margin of 200 the box started at y=182, against the spec's own rule that nothing sits in the top 200 px; at 240 it starts at y=222.
- **The hook wraps and is limited to 60 characters.** The spec's file sets `WrapStyle: 2`, which disables wrapping, and a long hook ran off both edges. Hook lines carry `{\q0}`; 60 characters is two lines.
- **The hook's time on screen is a setting** (`--hook-seconds`, and "Hook time" in the dashboard), added at the owner's request. The spec fixed it at 2.5 seconds, which stays the default. 0 means the whole clip, which is the footage only: the hook never sits on the end card. A time longer than the clip is cut to the clip.
- **In the `facecam` layout the hook sits under the webcam panel** (margin: the panel's height plus 30; 670 for the old fixed panel), so it does not cover the face.
- **The content is a box of its own (2026-11-21, at the owner's request).** With the panel following the webcam, the content window was worked out from the webcam (the middle of the gameplay in the lower panel's shape), so resizing the webcam reshaped the content too, which the owner did not want. The content is now a second box, blue beside the webcam's yellow, moved and resized on its own and saved as `game`. Two boxes and one screen leave one thing free: the webcam's shape sets the split, and the content box, of any shape, is fitted into what is left. A content box in the panel's shape fills it; in another shape it is shown whole over a blurred copy of itself, the same way as the center layout's wider crop, rather than cropped, since cropping would cut away part of what the owner chose and the page would not show which part. "Fit to the panel" makes the box the panel's shape inside where it was. Looked at: a wide content box under a 4:3 webcam came out whole with blur above and below, and fitted, it filled the panel. Driven on the owner's dashboard: dragging the webcam's corner left the content box as it was (886×1080 before and after), dragging the content's left the webcam's, and "Fit to the panel" made it fill the panel; no console messages.
- **The webcam panel takes the webcam's shape (2026-11-21, at the owner's request: "not all cams are 16:9").** It used to be a fixed 1080×640 and the box on the page was locked to that shape, so a 4:3 or square webcam had its top and bottom cut away. Now the box takes any shape (with 16:9, 4:3 and 1:1 buttons), and the panel is full width and as tall as that shape makes it, made even downwards (a 16:9 box gives 606, 607.5 exactly), within 480 to 1152 px: below 480 the webcam is a strip, above 1152 the gameplay would have less than 40% of the screen. Outside those limits the box's edges are cropped and the page says so. The gameplay window gets the lower panel's shape. The height is saved with the clip (`camHeight`), so a re-render keeps it, and a clip from before has none and keeps 640: its picture does not change. Looked at: a 4:3 test webcam with a red border came out whole, border on all four sides, in an 810-pixel panel, with the hook just under it; and on the owner's dashboard the shape buttons and a free drag changed the panel and the gameplay window as expected, with no console messages.
- **An on-screen disclosure is written before the hook** in the subtitle file. When both are on screen, the renderer stacks the earlier event above the later one; measured, their boxes touch and do not overlap.
- **End-card text uses the hook style at a bottom margin of 540.** Its box then ends at y=1397, level with the captions.
- **Captions are size 76, down from 88 (2026-11-21, at the owner's request: "a little bit smaller").** The widths were measured again rather than scaled: the same six phrases rendered through the subtitles filter with the bundled font gave one em as 66.5 px (77 at 88), and the estimate is within 10 px on all six. A line of wide letters needs less shrinking now (94% instead of 81%). The owner also asked for the captions at the very bottom of the content; that was not done, and the owner was told why: the bottom quarter of a vertical video is covered by the apps' own name, description and buttons, which is what the 520-pixel bottom margin keeps them clear of. Clips rendered again from now on get the new size.
- **Wide caption lines are shrunk.** Captions never wrap, and an 18-character line of wide letters ran off the frame. `src/captions/width.js` estimates the width from the font's advance widths (one em is 66.5 px at the caption size of 76, plus 12 px of outline; at the earlier size of 88 it was 77 px and within 3 px of the rendered width on six test phrases, at 76 within 10 px, and the test allows 10 px) and adds a scale tag when a line exceeds 960 px.
- **`--no-captions` skips only transcription.** In the spec it also skipped building the subtitle file, which would have removed the hook.

- **Swear words are drawn with a letter covered** (`F*CK`, `SH*T`; 2026-11-23, at the owner's request, "check what YouTube actually requires"). YouTube's advertiser-friendly guidelines (https://support.google.com/youtube/answer/6162278, read on that day through a summary of the page, not word for word) put "abbreviated or obscured profanity" in the title, thumbnail or video in the full-ads tier, and describe obscured as bleeping or muting the word, or "covering written words with black bars, symbols, or text added in post-production". The page does not mention captions; covering with symbols is the nearest wording. Moderate words ("shit", "bitch", "asshole") spoken in a video keep full ads anyway, stronger ones at the start or through most of a video limit them, and hateful words get none even when covered. So this changes what is written, which is what was asked; it does not make a clip with a spoken strong word safe. Titles are the strictest place and `post.txt` is not touched.
  - Applied when drawing, not to the transcript: the checks, the word-fixing screen and a later render with it turned off all need the real words.
  - One star per letter. `groupWords` splits on length, so a cover that changed the length would regroup the captions; a test compares the lines with it on and off.
  - A shouted word is transcribed with stretched letters ("fuuuck"), so words are compared as runs of one letter; hateful words are compared as written, because one of them with doubled letters taken out is the name of a country.
  - The star's width (389 thousandths of an em) was read from the font file; before, it counted as the widest letter and a covered line would have been shrunk for nothing. A frame was looked at: `WHAT THE F*CK`, `HOLY SH*T` and `F***CK` read clearly at size 76.
  - **The voice is muffled for the length of the word** (the owner chose a muffle over a beep or silence the same day, "to keep the feeling of what he is saying but not fully clear", knowing YouTube names only bleeping and muting as obscured). Three low-pass filters at 300 Hz, switched on only inside a window over the word, with a little gain. The window was at first the whole word with 0.08 s before and 0.12 s after; the owner listened, liked it, and asked the same day for less than the whole word, so it is now the middle 60% of the word, and never less than 0.12 s (a word shorter than that is muffled whole). The measurements below were taken with the first window; the real "What the fuck" was measured again with the shorter one (see the last line). Measured, not listened to:
    - On a steady 1000 Hz tone the level inside the window fell by 60 dB and was unchanged before and after it.
    - On 24 s of a stream recording, six ordinary words were muffled at four strengths and the local speech recogniser was asked what it heard: at 500 Hz twice it still recognised 1 of 6, at 350 Hz twice 2, at 250 Hz twice 3, at 300 Hz three times none. (The recogniser's answers move a lot between runs, so this is a rough guide.)
    - On a real "What the fuck", said twice in one of the owner's fetched parts: the recogniser heard both on the plain clip and neither on the muffled one ("What is this defense man"); the level during the word fell by 6.5 dB and by 16 dB, and half a second before it was the same to a tenth of a dB.
    - It muffles everything at that moment, the game sound too, and only words the recogniser caught.
    - With the shorter window (0.19 s of a 0.32 s word) the recogniser wrote "What the f**k" for the same two moments: it no longer hears the word plainly, but it guesses it. The owner was told that this is weaker than the first window. `MUFFLE_PART` in `src/captions/mask.js` is the one number to change.

## Transcription

- **faster-whisper, model `small`, `int8`, on the CPU**, as in the spec (a whole video's transcript for suggestions moved to an NVIDIA card where there is one on 2026-11-23; captions did not). About 5 seconds for a 30-second clip. The model makes mistakes with names. `npm run setup` installs the latest faster-whisper without pinning a version; 1.2.1 is the one that was tested.
- **Word times are moved off pauses** (`src/captions/pauses.js`). With the spec's settings the first word after a pause was timed 0.25 to 0.6 seconds early, because the model stretches it back over the silence, so its caption appeared before it was spoken. Pauses are found with ffmpeg as stretches at least 15 dB quieter than the clip's average level for 0.25 seconds or more. A relative level means background music simply yields no pauses. This is separate from the grouping rule in `src/captions/group.js`, which starts a new caption line after a gap of more than 0.4 seconds between two words' times.
- **Stretched words are moved onto the voice, under game sound too (2026-11-22).** The owner's clip "what-just-happened-here" (a streamer shouting "what happened" three times over GTA sound) had captions up to 2.6 s early. The voice band (300–3000 Hz), measured every 0.25 s, had the shouts at 10.75, 13.25 and 15.0 s, about 20 dB over the game sound between them; the transcriber started each "what" where the previous word ended (9.56, 11.48, 14.04) and its ends were right to within 0.1 s. The pause rule above changed nothing, because the game sound never drops 15 dB below the clip's average. `src/captions/onsets.js` reads the voice band every 0.05 s, and in a word longer than 0.5 s takes the last stretch within 10 dB of the word's loudest moment, a stretch ending at a quieter gap of 0.2 s or more; the start moves there, only ever later, and the end stays. The first version took the first such moment and missed two of the three, because the loud tail of the word before sat at the start of the stretched word. After it: 10.85, 13.3 and 15.0 s. On ordinary talking (two other 30 s parts) 5 of 52 words moved, four of them by 0.2 s or less. A frame at 13.6 s of the re-rendered clip shows the streamer mid-shout under "WHAT HAPPENED". Not listened to. One word ("Check" at 21.0 s) had no loud stretch to go by and was left; it may be early.
- **Captions are transcribed without the voice-activity filter (2026-11-22).** On the same clip the filter dropped the last sentence and put "check" 6.7 s before "your percent", which follows it in one breath. Compared on the eleven parts in `in/` that day, without the filter: about the same on talking, and much more on shouting over game sound (one part 4 words with it, 42 without), and nothing lost anywhere. Without it the model wrote "You" on 20 s of silence and on 20 s of noise, as Whisper is known to; `hallucination_silence_threshold=2.0` removed both and changed nothing on the parts with speech but one, where it kept more words. The batched whole-video transcript keeps its own pieces, which it needs to batch, and is unchanged. This replaces the setting the caption timing was first measured with (see "Tighter voice-detection settings" below), so clips cut from now on can differ from earlier ones of the same range.
- **A punctuated prompt for the model was tried and rejected.** It improved timing but inserted words at the start of clips. Tighter voice-detection settings did not improve timing consistently.
- **When the transcriber is not installed, the clip is made without captions and a warning is printed.** An error would have broken every `cut` on a machine without Python set up.
- **`clipper render` re-renders from an edited `work/transcript.json`.** The spec said a run could be "resumed" without defining how; this is the one way.
- **Whisper stays local.** On 2026-11-19 the owner considered replacing it with a hosted speech-to-text service (no Python, about 950 MB of disk freed, likely better accuracy, but paid per minute and the audio is uploaded) and chose to keep the local model. A text model such as Claude cannot replace it, since it does not take audio. A hosted service could still be added later as an option behind the interface in `src/transcribe/`.
- **Timing of words in the middle of continuous speech has not been measured.** The owner was asked to judge it by eye.

- **Captions are transcribed twice where the first pass leaves a long silence** (2026-11-23). The owner cut a 13-second clip whose first 5.5 seconds had no captions, though a sentence with a swear word is shouted there. Tried on that sound: the plain pass (no voice filter, as chosen on 2026-11-22) starts at 5.5 s whatever its silence and no-speech settings; the pass with the voice filter, and the batched one, hear a sentence at 1.3 to 3.3 s. The filter was turned off because it loses sentences under game sound, so neither is right alone. Now the plain pass's words are kept as they are, and only where they leave 1.5 s or more with no word is a second pass with the filter asked, and its words used there (`src/transcribe/fill.js`).
  - The second pass is unsure exactly there. Run three times it wrote "What the fuck? Who's shaking", "You should get" and "What the fuck?! Who's taking" before the same "the fucking car" each time; the changing words had a sureness of 0.03 to 0.24 or no length, the steady ones 0.7 to 0.97. So a word is taken only at 0.4 or more and with some length. On that clip this gives "fucking" or "fucking car?" at 2.3 s, run to run: the swear word is caught, covered and muffled, the rest of the sentence is not reliably captioned.
  - It costs a second run of the recogniser for a clip with a long silence: 11 and 20 s were measured for the two passes on the 13-second clip; one pass alone was not timed.
  - A real cut of that range afterwards gave "THE F*CKING CAR" at 2.22 s, two muffled moments, and the sound 3 and 4.6 dB lower inside them.
  - If the second pass fails, the first pass's words are used and nothing is said. A stop still stops.
  - Not tried: a larger speech model on such sound, which is the real cure for words it cannot make out.
- **The second pass listens to each silent stretch on its own** (2026-11-24, replacing the pass with the voice filter over the whole clip from the day before). The owner cut a 27.5-second clip whose last 10 seconds had no captions, though "What the fuck" and more is shouted there. On that sound every way of hearing the whole clip stopped at 17 s: plain, with the voice filter, and batched. Given only the last seconds, the recogniser heard about twenty words there.
  - One call for each stretch. Two stretches in one call (`clip_timestamps` with two ranges) gave the first and nothing of the second.
  - What it hears is judged a sentence at a time, not a word at a time: words with no length are dropped, and a sentence is used whole when the recogniser is sure of its words at 0.35 on average and its piece is not more likely to hold no speech (0.6). Word by word, yesterday's sentence came out as "the out of here", without its swear word. On the two clips the sentences that fit came out at 0.5 to 0.8, a lone "Fuck!" at 0.39, and the odd ones ("No!", "Hey!", a repeat piled up at one moment, an echo of the word before a silence) at 0.11 to 0.30.
  - Result: today's clip gets "What the fuck! Fuck! see it! Now the car! I see it! bitch! Fuck you, no!" in its last seconds, yesterday's "Get the fuck out of here!" or "Who's here to the fucking car?" in its first, run to run: the swear words are caught, the exact words of a shouted sentence are not certain.
  - It also hears voices that are not the streamer's. In a 3-second pause of today's clip it wrote a line of the game ("Take us to ... speed shop on North East 16th Street"), which the first pass had left out. The owner was told; such words can be removed on the clip page.
  - Time: 7 to 14 s in all for these two clips; only the silent stretches are heard twice.
  - **It repeats on the silence that is left** (`fillInRounds`, the same day). The owner cut the same moment as a 60-second clip, and the "What the fuck" at 20.5 s was missing again: given the stretch from 17 to 30 s, the recogniser skipped to 25 s, just as it had in the whole clip (2 of 3 tries; the same with its guessing turned off), while the stretch from 17 to 25 s gave the words every time. So after each round the silences are worked out again and the ones not yet heard are listened to, up to four rounds, never the same stretch twice. Three runs on that sound afterwards all had "What the fuck" at 20.5 s; a second "What the fuck are you saying" at 23.4 s came in two of the three. The 60-second clip took 56 to 81 s to transcribe this way on the first machine.
- **Captions use the larger speech model, `large-v3-turbo`** (2026-11-24). After the fixes above the owner still found the 60-second clip not fully captioned, and named the cause: where the game is loud the streamer's voice is ignored. Measured on that clip's sound:
  - Cleaning the sound first with ffmpeg (voice band with levelling, FFT denoise, a compressor) changed almost nothing: the small model's plain pass heard 1 word between 17 and 30 s either way.
  - One plain pass: small 66 words, with 1, 0 and 0 in the three loud stretches (17 to 30 s, 32 to 43 s, 52 to 60 s), in 7 s; `large-v3-turbo` 104 words, with 8, 7 and 15 there, among them the "What the fuck?" at 20.4 s, in 17 s (23 s with the model's loading; 4 threads were faster than 8, 23 s against 30 s).
  - With the second pass on the silences: 134 words, 27, 16 and 15 in the loud stretches, the same words on both of two runs (the small model's answers changed from run to run).
  - The second pass is the slow part now: each stretch costs about 5 s whatever its length, plus about 4 s to load the model for each round. So it is two rounds, not four: one round gave 118 words in 79 s, two 134 in 101 s, four the same 134 in 107 s.
  - The owner agreed to the download (about 1.6 GB) before it was made. Whole-video transcripts keep the small model: they are only read, and speed matters there.
  - Not done: the second pass in one process (the model is loaded again for each round), captions on the home PC's graphics card, and separating the voice from the game sound before recognition, which was the other choice offered.
- **The second pass was removed the same day** (2026-11-24). With the larger model the owner found captions that made no sense: a line at a moment when the streamer says nothing ("We'll be right back"), a police radio line, and game characters' speech mixed into his. On that 37-second clip the larger model's first pass alone wrote "RUN! / I'm gonna show the fucking ground! / Lushia get in! / Lushia get the fucking car! / Oh my god! / What the fuck? / Would this be the man carrier? / Well anyways...", which matches what the owner said is spoken there; every wrong line came from the second pass. It listens to the stretches where the first pass heard nothing, and with a model that hears the streamer under game sound, those stretches are where he is silent: what is left there is the game, or nothing, and the recogniser makes a sentence of either. So captions are one pass again: 23 s instead of about 100 s for a minute of sound. `src/transcribe/fill.js` and the script's `pieces` mode are gone; the notes above are kept for what was measured.
  - Before finding that, ways to tell the streamer's voice from the game's were tried on two of the owner's clips, and none held: how the sound sits between left and right (a game line sat in the middle like the voice); a voice fingerprint (`sherpa-onnx` with a wespeaker model: under loud sound the fingerprint was mostly the game's, sentences from a loud stretch were 0.84 to 0.89 like a stretch with no speech); the same after cleaning the game sound away with a speech-enhancement model (the cleaner removes the game almost wholly, 53 dB, but also damages shouting: the recogniser heard no better on the cleaned sound, and the streamer's own lines scored from 0.44 to 0.89 against one another); movement of the mouth on the webcam (on this channel the webcam is a drawn avatar over the game, so the game moves behind it); and the avatar's pink mouth (too few pixels to tell from the picture behind). The cleaner did show one thing reliably: where a written line has no speech under it at all (-94 dB left for "We'll be right back"). That could check a caption line if made-up lines come back.
  - The library and the three models used for those tests (about 57 MB) were removed afterwards; nothing in the tool uses them.
- **Captions are heard in pieces of about 10 seconds** (2026-11-24, the last change of that day). With one pass of the larger model the owner cut a 46-second clip whose captions covered about 15 seconds of it. For a while a `.env` line (`CLIPPER_CAPTION_MODEL=small`, made from an example the owner had been shown) had also put the small model back, which hid this for two clips. On that clip's sound, with the larger model:
  - As it was (the whole clip in one call): 38 words, a word in 18 of the 46 seconds. With the voice filter: 34 words, 14 seconds. Batched: 35 words, 21 seconds. Without memory of the earlier text: 67 words, 27 seconds. In 15-second pieces: 53 words, 21 seconds. In 10-second pieces, each its own call: 95 words, 37 seconds.
  - So the recogniser hears the speech when it is given little at a time, and skips when given much. This is what the removed second pass had stumbled on (a 13-second stretch skipped, an 8-second one heard), but done everywhere and not only where the first pass was silent, so it does not single out the stretches where the streamer says nothing.
  - Each piece ends at the quietest twentieth of a second within 1.5 s of its 10-second mark, so a word is not cut in two (`pieces_of` in `scripts/transcribe.py`).
  - As built: the 46-second clip 97 words, 40 of 46 seconds, 33 s to transcribe; the 60-second clip 136 words, 51 of 60 seconds, with "What the fuck?" at 21 s, 45 s to transcribe. A real cut of the 46-second range: 42 caption lines from the first second on, the longest stretch without a new one 3.5 s, 76 s in all.
  - It writes every voice it hears. In the 46-second clip that is a scene of the streamer with other characters ("they have you surrounded", "just give it up"), and in the 60-second one a line of the game ("Take us to Stockyard Speed Shop"). The owner was told that telling the streamer from the others was tried and did not hold, and that lines are removed on the clip page.
  - Names come out by ear (another streamer's name was written two ways, both wrong; "Lushia"). A brief's `replacements` fix a name for every clip made with it.
- **"Drop game voices": a voice model as a judge, built and removed the same day** (2026-11-24). The owner tried it and had it taken out with everything else layered on captions that day: "we made it overcomplicated, downloaded extra tools ... and we still have the same issue". Only the larger speech model was to stay. The code, the checkbox, the voice sample on the Sources page, the library and the model are gone; what follows is kept for what was measured, in case it is asked for again. With every voice written, the owner asked again for the game's characters to be left out, and later said a second streamer on a call must be kept. VoxLock, a model that locks onto the main voice and takes the rest away (sherpa-onnx 2.0.3, about 90 MB with the library), was tried on two clips; the owner listened to its output for one: the game's characters were almost gone, and so was part of the streamer's "what the fuck" under a crash.
  - So its sound is not used. Captions are written from the sound as it was, and for each line the judge says how much is left after VoxLock (the best half-second, in dB against the raw sound). The lines fell into two heaps, 0 to -18 dB and -22 to -41 dB; the line is drawn at -20.
  - A line with a swear word is never dropped. The streamer's "What the fuck?" had -36 dB left, the least of any line, and it is the line the owner most wants. The price: a game character who swears stays.
  - The voice sample. With the streamer's own voice as the sample, with none, and with a stranger's, the clear lines were kept and the buried ones dropped alike, which at first looked as if the sample did nothing. A real cut showed the difference at the edge: with no sample 3 lines of the 60-second clip were dropped, with the streamer's voice 6 ("Hey, down the car!", "Hey, bro, get him over my brother!", a third "Get out of the car, pal!", "No!", "You know!", "They caught him!"), which is the set the owner had heard as gone. So each channel can have a sample, uploaded on the Sources page; without one the option still runs.
  - It does not know who is speaking. In the scene with the second streamer one sample of the streamer kept both men at about 0 dB, which is what the owner wants; a game character who is loud and clear is kept too ("Take us to Stockyard Speed Shop" stayed either way).
  - What the page says about a sample is only its length and loudness. A sample tested against itself would always pass, so no such test is shown.
  - Time: 16 s for the judge on the 60-second clip (145 s in all against 124 s without).
  - Voice samples were added to what syncs, and taken out again with the feature. One sample the owner had uploaded (`data/source-voices/`, 27 s) was left where it is, on the machine and in the data repository, for the owner to keep or delete.
  - Not tried: a clean uploaded sample (the test sample was 4.5 s cut from the clip itself, with game sound under it); other channels; other games.

## Briefs, post text and checks

- **`captionMustInclude` was renamed `descriptionMustInclude`.** In the spec "caption" meant both the post's text and the burned-in subtitles. In this tool it only means the subtitles. The old name is rejected with a message.
- **`--title` and `--desc` were added.** The spec's `post.txt` needed a title and description but had no source for them. The title defaults to the hook.
- **`post.txt` is written whenever there is a brief, a title or a description.** At first it needed a brief, and the dashboard hid the two fields until one was chosen. The owner looked for them and did not find them, and the title and description from an AI suggestion were being dropped. Without a brief the file holds the title and description only: no hashtags, and no rules are checked.
- **Rules that can be judged early are checked before rendering**, and a failure stops the run before a clip folder is made. The spec checked only after the render.
- **A failed rule after rendering leaves the clip but exits with an error code.** A forbidden term found in the captions may be a transcription mistake the owner can fix.
- **Forbidden terms are also looked for in the transcript, the disclosure and the end-card text.** The spec checked only the title, description and hook. Terms match whole words, ignoring case.
- **The end card is appended after the footage** as a silent tail, and counts toward the brief's length limit. The spec covered the last seconds of the footage with it, which hid content. `--start` and `--end` now always mean what is shown.
- **The end-card image is optional and is placed over a plain dark card.** Placed straight over the footage, a logo with a transparent background would let the frozen last frame show through. This was checked by hand with two generated pictures, one opaque and one with a transparent background; the tests cover only the filter graph's text.
- **`keepFullFrame` was added.** A brief that needs the whole source frame visible passes only with the `blur` layout.
- **`replacements` was added** for words the transcriber gets wrong every time, such as brand names. A key may be several words. They are applied once, when a clip is cut, and the result is saved in the transcript.
- **`platforms` is only printed in the to-do list**, and all optional hashtags are appended after the required ones. The spec did not say what either did.
- **Brief files are validated strictly.** A misspelled field is an error, not a rule that silently never runs.
- **Each clip's `meta.json` keeps a copy of the brief** it was made with, so a later render does not depend on the brief file. It also stores the source video and the end-card image as absolute paths, so a clip folder cannot be re-rendered on another machine.

## AI help

The spec planned one AI feature for version 1.1: `clipper suggest`, through OpenRouter. On 2026-11-19 the owner asked to connect AI and offered an OpenAI key, so it was built on OpenAI directly. The same day the owner asked whether the Claude command line could be used instead of a key, and it was added as a second service and made the default where it is installed.

- **Two features, both proposals only:** suggested moments (with a hook, title and description for each) and caption word fixes. The owner presses the button that cuts or saves.
- **Whisper still does the transcription, locally.** A text model cannot take audio, and the owner chose to keep the local model (see Transcription).
- **Two services behind one interface** (`src/ai/client.js`): Claude through `claude -p`, and OpenAI. `CLIPPER_AI` chooses; with no choice, Claude is used when the `claude` program is on the PATH. Claude needs no key and no separate bill, at the price of sharing the owner's plan limits and working only where Claude Code is installed and logged in.
- **How Claude Code is called:** `claude -p --output-format json --json-schema <schema> --tools "" --strict-mcp-config --no-session-persistence --model sonnet --system-prompt <instructions>`, with the transcript on standard input, from the temporary folder. The answer is read from `structured_output` in the JSON it prints. Checked on Claude Code 2.1.328.
- **The schema's `$schema` line must be removed** before it is passed to `--json-schema`. zod adds it, and the command line then fails with "no schema with key or ref". The first real run failed for this reason while the tests passed, because tests use a stand-in service.
- **`--bare` is not used.** It was left out so the command line keeps using its normal login.
- **Model `gpt-6.2-sol` for OpenAI**, the middle of OpenAI's current range, confirmed available by listing the key's models. `CLIPPER_AI_MODEL` changes it. Model names were taken from OpenAI's documentation on that day, not from memory.
- **The official `openai` package with its zod helper** (`zodTextFormat`, `responses.parse`), checked offline against the installed zod 4 before use.
- **The schema sent to the model is plain**: every field required, no length or range rules. Limits are enforced afterwards in `tidyMoments` and `tidyFixes`, which also survive an answer that is wrong in every field.
- **Suggested times are moved onto real words** of the transcript, with 0.1 s before the first and 0.25 s after the last, and a moment that is too long is shortened at a word.
- **Each suggestion is run through the brief's ordinary rules** and shown with what it would fail. The model is told the rules but is not trusted to follow them.
- **The whole-video transcript is kept in `out/.cache`**, named by the file's name, size and date, because making it takes minutes: 137 seconds for a 10-minute video on the first development machine, against a few seconds once kept.
- **The whole-video transcript is made batched (2026-11-21)**: the owner found a 60-minute video took 12 minutes, unusable. On their machine (16 cores under WSL), 116 s of speech took 48 s the plain way with faster-whisper's 4 threads, 228 s with 12 threads, 16 s batched (`BatchedInferencePipeline`, 8 pieces at once) with 4 threads and 13 s with 8: about 3.6 times faster, 230 words against 232. Only this transcript is batched, with 8 threads; captions keep the plain way with 4, which they were measured with. Not yet timed on a whole hour.
- **Videos over 60 minutes are refused** (3 hours since 2026-11-23; see "Suggestions on videos up to 3 hours") with a message, not cut short silently. One second over is let through (2026-11-21): a fetched hour, "0m00s-1h00m00s", was 3600.001 s and was refused with "this one is 60 minutes". The message now gives the exact length.
- **A word fix replaces exactly one word with one word.** That keeps the word times valid. It cannot remove a stray word: "the Sandro Martinez" became "the Lisandro Martínez".
- **`suggest` prints only numbers in its `cut` command.** A hook written by a model, pasted into a shell line, could run commands.
- **Measured through Claude Code on the same video:** four moments in 6.4 seconds once the transcript existed, and through the dashboard's server three moments and one word fix (Sandra to Lisandro). An earlier single test corrected "noses" to "notifications", where OpenAI had proposed "notis".
- **Measured through OpenAI on the owner's 10-minute video:** 5,295 tokens in and 545 out for four moments, all four sensible and inside the length limits. In the dashboard, "Suggest moments", "Use this", the timeline marks and "Suggest fixes" were pressed and worked; the fixes proposed were noses to notis, Sandro to Lisandro, and Martinez to Martínez.
- **The suggestion in use is highlighted** in the list, on the timeline and above the range fields, and stays highlighted while the range is adjusted by hand. The owner lost track of which suggestion was being cut. Suggestions sent for cutting are marked "Already cut" until the page is reloaded.
- **Hooks from the AI (2026-11-21, at the owner's request: a button beside the hook box).** Three hooks for the range being set up, in one request, shown as buttons that fill the box when clicked; nothing is filled in by itself. The words come from the kept whole-video transcript when there is one, cut to the range and moved to the clip's clock, so pressing it costs no transcription; otherwise only the range is transcribed, in a temporary folder that is removed. Only the range's words and the brief's rules are sent. What comes back is fitted to the 60-character limit at a word, cleaned of subtitle commands (`cleanOverlayText`), stripped of quotation marks, kept without repeats, and checked against the brief's on-screen and forbidden-word rules, which the page marks. Run as a job, like the other AI requests, so the side column shows it and Stop works; its "ready" notice is not shown, since the answer appears beside the box. Tested with a stand-in AI and transcriber; the button was looked at on the owner's dashboard but not pressed, so no real answer has been seen.
- **Not verified:** the "Already cut" mark in a browser, a suggestion run with a brief against the real service, saving AI word fixes and re-rendering from the page, and how good the suggestions are on other kinds of video.

## Dashboard

The spec ruled out a web interface for version 1 and listed "a small review interface" under later ideas. The owner asked for a dashboard with Vue and a Node API once version 1 worked, because choosing times and crop positions from the command line means guessing.

- **Two front ends, one engine.** `server/` calls the same functions as `src/cli.js`. The only additions to `src/` were an optional progress callback, `describeLayouts`, and three small functions for reading and saving a clip folder's files.
- **Express and Vue with Vite**, chosen with the owner. No UI library, router or store: there are two screens.
- **Port 4517**, because 3000, 8000 and 8080 are taken on the owner's machine. `CLIPPER_PORT` changes it.
- **It listens on `127.0.0.1` and checks `Host` and `Origin`.** The server can start ffmpeg and read the `in/` folder, so it must not be reachable from the network or from other web pages in the browser. Express listens on every network interface unless told otherwise.
- **Express passes a failure to start to the `listen` callback.** The first version printed "dashboard running" when the port was already in use.
- **One background job at a time**, polled by the page. A cut takes about a minute, far too long for one request.
- **The crop frame drawn over the video uses the engine's own numbers.** Checked by dragging the frame in the browser, cutting, and comparing a frame of the clip with the same crop taken from the source: they matched, and `cropX` in `meta.json` equalled the value on screen.
- **Progress lives in one shared list (`web/src/jobs.js`), not in each screen.** The owner started a cut, moved to another video, came back, and found no sign of it: each screen had kept its own progress and lost it when left. The owner offered two fixes, freezing the screen or showing the state; showing it was chosen because the server queues jobs, so work can continue. The list is read from the server, so it also survives a reload. Checked in Chrome: the bar stayed across screens, came back after a reload in the middle of a cut, and "Open" led to the new clip.
- **A job can be stopped from "Activity"** (2026-11-20, after a fetch from a live stream ran without end and the owner had no way to end it). A job that is waiting is finished at once and never starts; one that is running has its program ended.
  - **The signal is not passed down through the engine.** A job's work goes through many functions before a program is started, and threading a parameter through all of them, for seven kinds of job, would touch most of `src/`. The job's work is run inside `withStop`, and `run()` reads the signal from there.
  - **The program is interrupted, not killed.** Killed, the downloader left the ffmpeg it had started running: that was seen when the endless fetch was ended by hand. Interrupted, as with Ctrl+C, it ends ffmpeg itself. Tried on the live stream that caused this: the downloader and its ffmpeg were both gone 0.9 s after the stop.
  - **That same try showed the downloader reporting success when interrupted**: it closed its file and exited with code 0, and the fetch would have gone on to keep a 20-second recording as if it were the part asked for. So a stopped run fails whatever the program's exit code.
  - **The answer comes when the program has gone**, not when its output closes, since a program it left behind could hold the output open.
  - **A stopped cut removes its folder.** A failed cut keeps it, so what was asked for can be read; a stopped one was not wanted.
  - Checked in a browser on a scratch folder: a waiting cut and a running one were stopped with the page's buttons; both showed "stopped", no ffmpeg was left, no clip folder was left.
- **Clips can be deleted from the list**, at the owner's request: a trash icon, one confirmation in place, then the whole folder is removed for good. The owner asked for deletion, so nothing is moved to a trash folder. Two guards: `removeClip` deletes only a folder that holds a clip's `meta.json`, and the server refuses while any job is queued or running, since the folder could be the one in use. Deleting the newest clip frees its number, so the next cut reuses it. Checked in Chrome on a scratch folder: Cancel left the clip, Delete removed its folder and returned to the video screen.
- **Videos can be deleted from the list too**, at the owner's request, with the same trash icon and one confirmation. The confirmation says how many clips were cut from the video, because those clips can no longer be rendered again once their source is gone. Compilations that use the video are not counted; generating one then fails with "No such video." until the item is taken out.

## Plain parts

The owner asked for a way to take a piece of a video as it is: original size, no hook, no speech-to-text, kept in one folder apart from the clips.

- **Called "parts", with the command `extract`.** "Trim" was avoided because `--trim` already means cutting pixels off the edges, and "crop" already means choosing part of the frame.
- **One folder, `parts/`, with single files** named from the source and the range (`1_1m00s-1m30s.mp4`, then `_2` if that exists). A part has no working files, so it needs no folder of its own.
- **The picture is encoded again, not copied.** Copying is instant and lossless but can only start at a keyframe, so a part could begin several seconds early. Encoding makes the range exact: in the test a part starting between keyframes had its flash and beep within one frame of where they should be. The cost is time, about 17 seconds for 30 seconds of 720p at 60 fps.
- **Everything else is kept:** the size, the frame rate and every audio track. That is the opposite of a clip, which is 30 fps with one audio track.
- **A file being written starts with a dot** and is renamed when finished, so the dashboard never lists a half-written part.
- **Checked in Chrome on a scratch folder:** "Save this part as it is" showed its progress in the status area, the part appeared under "Parts" and not under "Clips", it opened and played at 1280×720, and the trash icon deleted it.

## Match cards and compilations

The owner asked for two more dashboard pages, to build "goal reaction" compilations: reaction clips with a card between them describing what happened. The request came with ffmpeg commands "tested with ffmpeg 6.1". They were tried on this machine's 4.4.2 before any page was built.

- **Each segment is given an explicit output length**, and a clip's sound is padded to it, so picture and sound are equally long in every segment.

Checked: a second run reused all five segments, changing one credit made only that segment again, and touching a source file made only its segment again. In the browser check a run that failed on its second item reused the first on the next run.

## Sources and fetching

Both specs ruled out downloading. The owner later asked to bring in parts of other channels' watchalong videos, and the two agreed on a narrow form of it.

- **Only channels marked as agreed.** The sources list (`data/sources.json`) holds each channel with a status. `fetch` refuses any video whose channel is not marked `agreed`. The status is set by the owner; the tool does not check it with anyone.
- **The page stopped showing the status and the note on 2026-11-20.** The owner reported that every channel on the list had agreed and that from then on only channels that have agreed would be added, and asked for a more compact page. The list is now one line per channel, a name and an address. A new entry is saved as `agreed`; the engine still checks that status, so a list saved earlier with other values behaves as before. The notes already written stay in the file.
- **The channel comes from the video's own data** (its channel id or handle, as the downloader reports them), matched against the address in the sources list. A link cannot pass itself off as another channel's.
- **A time range, never a whole video**, of at most 20 minutes, until 2026-11-21 (see the next entry). Watchalongs run for hours and the owner's disk had about 4 GB free; a goal reaction is a minute or two.
- **Whole videos too, up to 3 hours (2026-11-21, at the owner's request).** Once a fetch took seconds (see the relay below), the owner asked for whole videos, chose a 3-hour cap, and said not to worry about disk space because a video is deleted once it is clipped; the machine had 233 GB free. The length is YouTube's own, read before anything is downloaded; a video over 3 hours or without a length is refused, and live streams are refused as before. The free-space check is kept as it was. ffmpeg is given no `-ss` or `-t` for a whole video, so the fraction of a second that YouTube's whole-second length leaves off is kept: a 19 m 29 s video came out 1169.36 s long, in 14.9 s, 280 MB. If the fast way fails, a whole video goes through the downloader's own downloader rather than through ffmpeg, since only a range has to go the slow way. The file is named by its range like a part (`_0m00s-19m29s`). Suggestions still refuse videos over 60 minutes. From the Download page, the owner fetched a whole video of about 1.5 hours in about 20 seconds (2026-11-21, as reported by the owner).
- **YouTube links to one video only** (and, since 2026-11-23, Twitch past broadcasts; see "Twitch"), rebuilt from the 11-character video id before use, and passed to the downloader after `--`.
- **`yt-dlp`, installed into `.venv` by `npm run setup`** and brought up to date each time setup runs, because YouTube changes often and old versions stop working. faster-whisper is installed in a separate step without `--upgrade`, so running setup again for the downloader does not change the transcriber.
- **The file is named from the id checked in the link**, not from what the downloader reports, and a download that cannot be rewritten (see below) is removed. The rewrite works in a file whose name does not end in a video's extension, so the videos list never shows it half done.
- **No keyframe forcing.** The part is cut where the stream allows, which can be a few seconds before the asked start. That avoids encoding the picture again, and the exact start is set later when cutting.
- **A fetched part is rewritten so that nothing in it is hidden** (`removeHiddenLeadIn` in `src/fetch.js`). A part cut without encoding begins at the picture's last keyframe before the asked start, and the sound begins somewhere else again. The downloader's file marks both lead-ins as "skip this" (an edit list). On the first real fetch, 2026-11-19, a 70 s part of a 1080p60 AV1 video had 2.97 s of picture and 4.98 s of sound hidden this way, and the owner saw the sound almost 3 s away from the picture. Read by ffmpeg the file was in step (loudness against movement fitted best within 0.5 s, and clearly worse at 2 s and 3 s either way), so the content was right and the skipping was what went wrong. Which player misread it was not established. In Chrome, two frames taken after a seek were closer to the right picture than to the one 2.97 s earlier, but by a thin margin, and playback from the start was not measured.
  - The rewrite copies the picture as it is from its first frame, and cuts or pads the sound to begin at the same instant, encoding only the sound (AAC, 192 kbit/s). The part then starts up to one keyframe gap early (7 s in that video) and plays the same with the marks honoured or ignored.
  - The lead-in is measured by reading the same packet twice, found by its place in the file: once as the file asks to be played and once with `-ignore_editlist 1`. The difference between the two times is the lead-in.
  - Measured on that file after the rewrite: the picture is identical frame for frame (same MD5 over all 4378 frames), the sound sits 2.9666 s later than before, which is the picture's lead-in of 2.9667 s, and both streams start at 0.
  - Encoding the picture again would give an exact start, but costs a generation of quality on footage that is encoded once more in every clip and compilation.
  - A lead-in under 0.1 s on the sound alone is left: that is the ordinary start-up of a sound encoder, and every player handles it.
- **A live stream is refused** (2026-11-20). The owner asked for 11:00 to 11:15 of a stream that was still going on, and the job ran for over 17 minutes for a 15-second part. What was found: for a live stream the downloader gets only the live playlist and hands ffmpeg `-ss 660 -t 15`, which mean nothing there, so ffmpeg recorded the broadcast as it happened. When stopped it had 905 s of video in 252 MB, about 17 MB a minute, on a disk with 2.1 GB free, and would not have stopped by itself. `fetch` now reads YouTube's own state for the video (`live_status`) and refuses `is_live`, `is_upcoming` and `post_live` before downloading. `post_live` (ended, not yet prepared by YouTube) is refused out of caution: how a range behaves there was not tried. Checked against the same stream while it was still live: refused, nothing downloaded. The pieces a failed or stopped download leaves are now removed. Without that option a live stream can only be recorded from the present moment on, as it happens. So the only ways to get an earlier moment of a live stream are to wait for it to end, or to download everything from its start, which this tool does not do.
