# WLC Clipper

A Node.js tool that turns a local video file and a time range into a finished vertical clip: 1080×1920, 30 fps, burned-in captions, an optional hook line, and the on-screen text and hashtags a campaign brief requires. It is a personal tool for one owner. It can be used from the command line or from a dashboard in the browser, which is a small web server that only this machine can reach.

The repository is https://github.com/Mkaren92/wlc-clipper and it is public.

Read these before changing behaviour:

- `README.md`: how the tool is used, every command and flag, the brief format.
- `docs/decisions.md`: where the code departs from the spec and why, with the measurements behind each choice. Check it before "fixing" something that looks odd.
- `docs/roadmap.md`: what is built, what the owner still owes, what comes next.
- `docs/install-windows.md`: installing on Windows through WSL. Keep its versions, sizes and expected outputs true when setup, the commands or the test count change.
- `docs/build-spec-v1.pdf`: the original spec. The code and `docs/decisions.md` win where they differ from it.

## Commands

```bash
npm install                 # Node dependencies
npm run setup               # Python .venv with faster-whisper and yt-dlp; ask the owner first (see below)
npm test                    # vitest; some tests run the real ffmpeg
node src/cli.js --help      # the command line: probe, cut, render, check, suggest, extract, fetch
npm run dashboard           # build the pages, then serve them at http://127.0.0.1:4517
npm run dev:web             # only while editing the pages: live reload on port 4518
```

Needs Node 22.12 or later, and `ffmpeg` and `ffprobe` on the PATH built with libass. Captions and `fetch` also need Python 3 with the venv module. Sync needs `git` and an SSH key that GitHub accepts. It has only been run on Linux. On Windows it is meant to run inside WSL 2 with Ubuntu 22.04; `docs/install-windows.md` is the step-by-step guide, and it says which of its steps were run and which were written from Microsoft's documentation.

## On a new machine

1. Run `npm install` and `npm test`. These install only the dependencies the project already declares, so they need no extra permission.
2. Check `ffmpeg -version`. The measurements in `docs/decisions.md` were taken on 4.4.2.
3. Captions need three things that each install or download something. Ask the owner before each one:
   - the system's Python venv package, if it is missing (`sudo apt install python3-venv` on Ubuntu)
   - `npm run setup`, which installs faster-whisper and yt-dlp with pip into `.venv`
   - the first `cut` with captions on, which downloads the speech model (about 460 MB) to `~/.cache/huggingface`
4. Source videos go in `in/`. Clips come out in `out/`, plain parts in `parts/`, and saved matches, cards, combinations, compilations, the clubs list, the sources list with the channels' pictures and subscriber counts, and backups of the two lists in `data/`. The owner's own sound files for cards go in `sounds/`, and overlay images (logos) in `overlays/`. The tool creates all six. They are git-ignored, so none comes with a clone. What the owner chose to carry between machines comes over with the dashboard's "My data" page: by itself, through the owner's private data repository on GitHub (`src/sync/`; connect the new machine on that page, which needs `git` and an SSH key GitHub accepts), or by hand (`src/transfer/`): download a file on the old machine, load it on the new one.

Clip folders do not move between machines. `work/meta.json` stores the absolute path of the source video and of the end-card image, so `render` fails on a clip whose source is not at that path.

## How it is put together

A `cut` runs these steps in order (`src/cut.js`):

1. Probe the source with `ffprobe` (`src/probe.js`).
2. With `--brief`: load it (`src/brief/schema.js`) and run the rules that can be judged already (`src/brief/check.js`). A failure stops the run here, before any folder exists.
3. Create the clip folder, write `work/meta.json`, and with a brief write `post.txt` (`src/brief/postText.js`).
4. Extract the range's sound and transcribe it (`src/render.js`, `src/transcribe/`, `scripts/transcribe.py`).
5. Move word times off the pauses (`src/captions/pauses.js`) and stretched word starts onto the voice (`src/captions/onsets.js`), apply the brief's word fixes (`src/brief/replacements.js`), and write `work/transcript.json`.
6. Group words into caption lines and write the subtitle file (`src/captions/group.js`, `src/captions/ass.js`, `src/captions/width.js`).
7. Build the filter graph for the layout (`src/layout.js`) and run one `ffmpeg` pass (`src/render.js`).
8. Run all the brief's rules on the result and save them in `work/meta.json`.

`render` repeats steps 6 to 8 from the files in `work/`. `check` repeats only the rules of step 8 and writes nothing.

`src/ai/` holds the optional AI features: `suggest.js` proposes moments from a whole-video transcript, `fixWords.js` proposes corrections to caption words, and `suggestHook.js` proposes hooks for the range about to be cut (the "Suggest" button beside the hook box). They talk to a service only through the small interface in `client.js`, which picks one of two: `claudeCli.js` runs the Claude Code command line (`claude -p`) with the login it already has, and `openai.js` uses an API key. `src/env.js` reads settings from `.env`.

"Suggested moments" has two sources. The transcript (`src/ai/suggest.js`), optionally steered by event terms and guidance, and the chat: `src/chat/importChat.js` turns a YouTube chat replay (yt-dlp's `.live_chat.json`) or a chat file into `{ t, author, text }` messages, `src/chat/chatStore.js` keeps one chat per video in `data/chats/` and fetches a replay, `src/chat/terms.js` is the one word matcher both sources use, `src/chat/spikes.js` finds bursts of chat, `src/chat/presets.js` holds the Football and Gaming sets, `src/ai/chatCheck.js` is the optional AI check of chat moments, and `src/moments/merge.js` merges and ranks the two sources. "Clips from a stream's chat" on the Download page is `src/chat/chatClips.js` (look up, read the chat and the top comments, choose, download the parts through `fetchVideo`) with `src/chat/pick.js` choosing the moments from `src/chat/reactions.js` (what a message says: a reaction, noise or chatter) and `src/chat/comments.js` (timestamps viewers wrote in comments); a stream's chat is kept under its YouTube id by `streamChat` in `chatStore.js`. `terms.js`, `spikes.js`, `presets.js` and `merge.js` import nothing from Node, because the page imports them: the chat moments are worked out in the browser, so the settings change the list at once.

`src/part.js` is the one thing that is not a clip: `extract` saves a time range of a video as it is, at the original size, into `parts/`.

`src/cards/` draws match cards: `templates.js` has one function per kind of card that returns SVG, `measure.js` fits text without a browser, `config.js` holds the lists of goal and red-card types, `match.js` saves a match with its cards, and `clubs.js` keeps the owner's list of leagues and clubs (`data/clubs.json`) that a match's teams can be filled in from. `src/compilation/` joins videos and cards into one video: `timeline.js` is the saved format, `build.js` renders it, `description.js` writes the credits and chapters, and `sounds.js` holds the sounds played under cards: the built-in ones, made by ffmpeg, and the owner's files in `sounds/`. `src/combine/` puts two videos side by side and makes one video of them: `layout.js` holds the sums (lengths, the two halves, which part of a video shows) and touches no file, so the page's preview uses it too, `combination.js` is the saved format (`data/combinations/<id>/`), and `build.js` renders it. A compilation can use the result, as one more folder of videos named `combined`. All three are used only from the dashboard.

`src/sources.js` is the list of channels and whether each has agreed, `src/fetch.js` brings part of a YouTube video, or a whole one, into `in/` with `yt-dlp` and ffmpeg, reading YouTube through `src/rangeRelay.js` (its link and range checks are in `src/fetchLink.js`, which imports no Node module so the Download page runs the same checks), and `src/pictures.js` fetches the profile picture of each channel in that list (`data/source-pictures/`), which a compilation draws beside the channel's name where it is credited, and keeps its subscriber count for the Sources page, `src/live.js` asks which of those channels are live, and `fetchChatReplay` in `src/chat/chatStore.js` brings in the chat replay of a finished stream from one of them. They are the only code that takes anything from outside, apart from sync, which brings back only the owner's own data.

`src/backup.js` keeps a copy of the owner's two lists (channels, clubs) before each is written. `src/transfer/` moves the owner's data between machines: `contents.js` is the one list of what that data is, `tar.js` writes and reads the file it travels in, and `transfer.js` makes the download and does the two-step load. `src/sync/` keeps the same data the same on every machine through a private GitHub repository: `sync.js` does a round (and looking at an address, connecting, disconnecting), `git.js` runs git on the copy kept in `data/.sync/repo` and nowhere else, `merge.js` puts together a list changed on two machines, record by record, and `logos.js` turns the clubs list's logos into files and back.

`src/cli.js` defines the commands and flags. `src/run.js` spawns programs, and is where a running job is stopped. `src/time.js` parses and formats timestamps. `src/types.js` holds the shared JSDoc types.

### The dashboard

- `server/` is an Express server (`server/app.js`) that exposes the same engine functions over HTTP. It adds nothing of its own beyond listing files and running slow work as background jobs (`server/jobs.js`). `server/index.js` starts it.
- `server/chat.js` holds the routes for a video's chat (read, fetch, import, offset, remove, AI check) and for reading a kept transcript without transcribing; `web/src/components/MomentFinder.vue` is the "Suggested moments" panel of the cutting screen, which uses them.
- `server/sync.js` holds the routes for sync and keeps it going: a round when the dashboard starts, then a look once a minute. `web/src/sync.js` keeps how sync stands for the side column and the "My data" page.
- `server/cards.js`, `server/combinations.js`, `server/compilations.js`, `server/sources.js` and `server/transfer.js` hold the routes for the extra pages, and `web/src/pages/` holds the pages (`CardMaker.vue`, `Combiner.vue`, `CompilationBuilder.vue`, `Download.vue`, `Sources.vue`, `MyData.vue`). The Download page fetches through the same `POST /api/fetch` route in `server/sources.js`. The buttons at the top of the left column switch pages; the page is kept after `#` in the address.
- `web/` is a Vue 3 app built with Vite into `web/dist`, which the server serves. `theme.js` holds the colour palettes and works out every colour from them, `style.css` holds the styles every page shares, `NewClip.vue` is the cutting screen, `FramePicker.vue` draws the layout over the video, `ClipView.vue` shows a finished clip, `api.js` holds every call to the server, `jobs.js` keeps the list of work in progress that the side column and the screens read, and `live.js` keeps which channels are live, for the Sources page and the count in the side column. `ClubPicker.vue` is the list a streamer's club is chosen from.
- The command line and the dashboard are two front ends to `src/`. Behaviour belongs in `src/`, so both get it.

A clip folder is named after the clip's hook (`out/barca-wants-who`, then `-2`, `-3` when taken), or `clip-NNN` when there is no hook. It holds `clip.mp4` and `post.txt` for the owner, and a `work/` subfolder with `meta.json`, `transcript.json` and `captions.ass` for the tool. Folders from before `work/` existed have those files next to `clip.mp4` and must keep working.

## Rules that must hold

Each of these exists because something broke or the spec demands it. The evidence is in `docs/decisions.md`.

- **Never use ffmpeg's `-r` output option.** The frame rate is set by the `fps` filter at the start of the graph. `-r 30` put the picture two frames behind the sound.
- **`-ss` and `-t` both go before `-i`.** Limiting only the output lets the source keep playing under the end card.
- **Never put a path inside a filter graph.** ffmpeg runs in the clip's `work/` folder and the graph names `captions.ass` and `fonts` bare. Paths passed as their own arguments are fine.
- **Keep only the first audio track** (`0:a:0`), mixed to stereo. A plain part (`src/part.js`) is the exception: it is meant to be the source unchanged, so it keeps every audio track, the original size and the original frame rate.
- **Spawn with an argument array**, never a shell string. The tool does it through `src/run.js`.
- **The overlay is ffmpeg's last input, never a path in the graph** (`overlaySteps`, `overlayInput` in `src/layout.js`; `renderArgs` adds it after the end card's inputs). It goes over the picture and the end card and under the subtitles, from the first frame to the last. Without one the graph and the command are exactly as before (a test compares them). A 9:16 picture is a full-frame overlay, anything else a logo. The brief's `overlay` wins over one chosen on the page, and its check fails a clip rendered without it. The page names an image in `overlays/` (PNG or WebP); `meta.json` keeps its absolute path, like the end-card image.
- **Blur boxes cover the source frames, first in the graph** (`coverSteps`, `checkBlurs` in `src/layout.js`; asked for on 2026-11-21 to hide nudity in game footage). Each is in source pixels and clip seconds, on only between its start and end, straight after the `fps` filter and before the layout, so it covers the same thing in every layout. Without any the graph is exactly as before (a test compares them). A blur shrinks the box to about a sixteenth and grows it back before blurring, because a plain blur of a big box still showed shapes; keep it at least that strong. Saved as `blurs` in `meta.json` (`[]` for older clips). The page keeps them in the video's own seconds and sends them as clip seconds.
- **Text drawn on the video goes through `cleanOverlayText`**, because `{`, `}` and `\` are control characters in subtitle files.
- **The caption font is bundled** (`assets/fonts`), and `src/captions/width.js` holds widths measured for that font at `CAPTION_SIZE` (76 since 2026-11-21). Changing the font or the size means re-measuring the widths (and, for the font, the hook position and the end-card text position).
- **Captions stay 520 px above the bottom edge** (`CAPTION_MARGIN`): the apps cover the bottom quarter of a vertical video with their own text and buttons. The owner asked for them lower on 2026-11-21 and was told why not.
- **The facecam's webcam panel follows the webcam box's shape** (`camPanelHeight` in `src/layout.js`, 480 to 1152 px; asked for on 2026-11-21: "not all cams are 16:9"). Its height is worked out once, at cut time, and saved as `camHeight` in `meta.json`; a clip without it is from before and renders with the old fixed 640, so it looks the same as when it was made. The hook margin is `camHeight + 30`. The content under it is its own box (`game` in `meta.json`, `--game`; asked for on 2026-11-21, so that resizing the webcam never changes it): shown whole, filling the panel in its shape (`gameFit`) or over a blurred copy of itself otherwise; `fitGameToPanel` is "Fit to the panel". A clip without `game` takes the middle of the gameplay (`facecamGameWindow`), as before.
- **Everything `render` needs is saved in `work/meta.json`**: the source, the range, the layout options (with the facecam's `camHeight`), the hook, and a copy of the brief. The title and description are not there; they live in `post.txt`.
- **`render` never rewrites `post.txt`**, and checks read `post.txt` from disk, because the owner edits it by hand.
- **The brief wins.** Where a brief and one of the tool's defaults disagree, the brief's value is used, and the checks report anything the tool could not satisfy.
- **Brief files are validated strictly.** An unknown field is an error, so a misspelled rule cannot silently never run.
- **Do not invent a campaign's rules.** A brief is written from text the owner supplies.
- **The dashboard listens on `127.0.0.1` only**, and `onlyThisMachine` in `server/app.js` refuses requests whose `Host` or `Origin` is not its own. Without that, any web page open in the owner's browser could start cuts.
- **The browser sends names, never paths.** A video is a file name in `in/`, a clip a folder name in `out/`, a brief a file name in `briefs/`; the server resolves them.
- **One job at a time.** Two cuts at once could pick the same clip folder.
- **A clip is deleted only through `removeClip` in `src/cut.js`**, which refuses any folder without a clip's `meta.json`. The page asks for confirmation first, in the page itself and not with a browser dialog, and the server refuses while a job is running. A video in `in/` and a part are deleted by name with the same two safeguards.
- **A job is stopped through `withStop` in `src/run.js`, not by passing a signal down.** `server/jobs.js` runs each job's work inside it, and every `run()` started from that work, however deep in the engine, finds the signal there (Node's `AsyncLocalStorage`). A stop interrupts the program as Ctrl+C would, so the downloader ends the ffmpeg it started, and ends it outright after four seconds if it has not gone. A stopped run always fails with `STOPPED`, even when the interrupted program reports success, and the job's status is `stopped` whatever the engine's own error said. A stopped cut removes the folder it made; a failed one still keeps it. New engine code needs nothing for this as long as it starts programs with `run()`.
- **Work in progress is not kept inside a screen.** The pages read it from `web/src/jobs.js`, which asks the server (`GET /api/jobs`), so progress is still shown after moving to another screen or reloading.
- **The pages name no colour.** Every colour is a token (`--bg`, `--accent`, `--bad` and the rest) that `web/src/theme.js` works out from a five-colour palette, so a palette can be swapped by changing five values. `test/theme.test.js` holds each palette to readable contrast. A result (passed, failed, waiting) uses `--good`, `--bad` and `--warn`, never `--highlight`, which is green in one palette and orange in another. Three exceptions, on purpose: match cards use the teams' colours, the crop window over the video (`FramePicker.vue`) has fixed colours so it shows on any footage, and a player's stage is black, with white for the words on it (`Combiner.vue`, and the background of the result players).
- **Nothing is fetched to draw the pages.** System fonts and drawn-in icons (`web/src/components/Icon.vue`) only: no web fonts, icon sets or style libraries from outside.
- **The player's keys are ignored while a box, list or slider has the keyboard.** On a button or link only Space and Enter are left to it, because a button is where the keyboard is after choosing a video or pressing Play. Keys are matched on `event.code`, not `event.key`, so they work on the owner's non-Latin keyboard layout. The listener is removed when the cutting screen goes away.
- **The pages do not redo the engine's arithmetic.** The crop windows drawn over the video come from `describeLayouts` in `src/layout.js`.
- **A re-rendered clip keeps its address**, so the pages add a version number to it and the server sends it uncached. Otherwise the browser replays the old clip.
- **The AI key lives only in `.env` or the environment.** Never write it into a file that is tracked, a brief, `meta.json`, a log, or a message to the owner, and never print `.env` or `process.env`. To check that it is set, count the line (`grep -c '^OPENAI_API_KEY=' .env`).
- **Only the entry points read `.env`**: `src/cli.js` and `server/index.js`, through `loadEnv`. If a module the tests import loaded it, `npm test` could spend the owner's money. Tests use a stand-in for the AI service.
- **What a model returns is untrusted.** It is validated in our own code (`tidyMoments`, `tidyFixes`, `tidyHooks`, `tidyChecks`), checked against the brief with the ordinary rules, and only ever shown as a proposal: nothing is cut, saved or rendered without the owner pressing a button. Model-written text never goes into a shell command; `suggest` prints only numbers in its `cut` line.
- **Error messages about the AI service are written here**, not passed on from the service, whose own text can repeat part of the key.
- **Only text goes to the AI service**: transcript words, the brief's rules, the owner's event terms and guidance, and, only when the AI check of chat moments is ticked, chat messages' words and times. Never who wrote a chat message (the owner's choice, 2026-11-21), no audio, no video, no file names or paths.
- **With no event terms and no guidance, the transcript request is exactly what it was before they existed.** `test/fixtures/suggest-prompt-before.json` was recorded from the old code and a test compares against it; steering is only ever added after the old text. Change the fixture only on purpose, with a reason in `docs/decisions.md`.
- **The model's answer for suggested moments is kept per video and per set of inputs** (`moments-<hash>.json` in `out/.cache`); bump `RESULT_VERSION` in `src/ai/suggest.js` when the prompt or the tidying changes. A kept file without `label` or `matchedTerms` must still load.
- **A chat replay is fetched by the rules of `fetch`** (`fetchChatReplay`): a checked YouTube link to one video, the channel read from YouTube's own data and agreed in the sources list, nothing live or not yet prepared, and only the chat (`--skip-download`). A chat file the owner imports may be for any video. Messages sent before the stream began are skipped (they carry offset 0 and a shown time starting with "-"); authors are kept only as a one-way id (`authorId`), never a name. Chats stay on this machine: `data/chats` is not in "My data" (the owner chose so on 2026-11-21).
- **Clips from a stream's chat follow the owner's request of 2026-11-21**: a finished live stream's link, words or none, a number of clips; only those parts are downloaded, each `before`/`after` seconds (20/20; 15/15 until the owner asked for 40-second clips on 2026-11-22) around the explosion taken 5 s early for chat's delay, never overlapping. Matches (at least `MIN_MATCHING_MESSAGES` messages with the words) come first and the rest is filled with the biggest other explosions, as the owner chose. Thresholds are loosened step by step (`TIERS` in `pick.js`) until there are enough. The rules of `fetch` hold for every part; one failed part does not stop the others; the stream is looked up once.
- **Clips come from what chat says and where viewers point, not from how much chat writes** (2026-11-21: on the owner's 11-hour gaming stream the biggest bursts were 62× "1", 97× "!me" and 77× "3"). `readMessage` drops commands, poll votes and plain "yes"/"no" answers; `reactionStream` counts a pasted sentence of five words or more once; only reactions and messages with the owner's words count. Keep chat's own words (W, L, F, lmao, 💀) in `REACTIONS`, one list per kind. A moment two or more comments point to ranks with moments both sources found.
- **Comments are read only for clips from chat**, by `downloader.comments` (yt-dlp, top 500, no replies), only after the same checks as the chat (agreed channel, finished stream), and only their words and like counts are kept, never who wrote them. They are not stored. If they cannot be read, the clips come from chat alone.
- **Chat detection is the engine's, run in the page.** `detectSpikes` and `mergeMoments` are pure and tested; the page imports them and draws what they return, and redoes none of their arithmetic. The AI check is one request for all candidates, not one each, and its labels are only proposals: a disagreement with the event words is shown as "needs review", never written over them.
- **Claude Code is run as a question-answerer and nothing else**: with `--tools ""` so it cannot read or change files, `--strict-mcp-config` so no connected services load, `--no-session-persistence`, and from the system's temporary folder so it does not read this project's `CLAUDE.md`. Do not loosen any of these.
- **A card's preview and its PNG come from the same template function.** The PNG is drawn in the browser (`web/src/cardPng.js`), which writes the bundled font into the SVG first: a picture drawn from SVG cannot load a font from outside itself and would silently use another one.
- **The clubs list is the owner's.** `src/cards/clubs.js` seeds four leagues with club names and one colour each: La Liga and the Premier League as of the 2026–27 season, "Europe", leading clubs of Italy, France, Germany and Portugal chosen by hand, and "Champions League", the 36 clubs of the 2026–27 league phase from a table the owner linked. Which clubs are in the leagues was looked up on 2026-11-20 because the owner asked for exactly that; the colours are from memory. A club in two leagues is two entries. Do not look the list up again or change it for a new season unless the owner asks, never fetch logos, and do not add logos to the seed. The seed reaches only a new install: the owner's own `data/clubs.json` is changed only through `saveClub`, `removeClub`, `saveLeague` and `removeLeague`, after a backup, and a club that has a logo is never removed or replaced without the owner saying so. A club's logo is the same owner-chosen small PNG as a match's icon. A match copies what it takes from a club, so the list can change without changing saved matches.
- **Everything a person types into a card is escaped** (`escapeXml`), and a team colour is used only if it is a plain `#rrggbb` value.
- **Cards are text and plain colour, except club icons on the intro card.** The owner asked for icons on 2026-11-19, which lifted the earlier "text only" rule for that one thing. An icon is a picture the owner chooses from their own computer; the page shrinks it to a small PNG that is stored with the match (`isIcon` in `src/cards/config.js`). Never fetch, bundle or suggest a source for crests, and add no league logos, player photos or broadcast images.
- **The built-in sounds are made, not recorded.** `src/compilation/sounds.js` builds each with ffmpeg: a computer voice (ffmpeg's `flite` source, stretched with `rubberband`) and plain tones. Do not bundle, fetch or download sound recordings; a real recording comes only from the owner, as a file in `sounds/`. Change `SOUND_VERSION` when a built-in sound's recipe changes, or old copies and the segments made with them are reused.
- **Nobody can hear the built-in sounds while building them.** The owner rejected the first three. Check what can be measured (length, level, pitch, and the voice with the local speech recogniser), say plainly that they were not listened to, and leave the verdict to the owner.
- **A card with no length is shown as long as its sound**, rounded up to a whole frame, or 3 seconds when silent. A length the owner typed is kept: a longer sound is faded out at the card's end, a shorter one is followed by silence. A sound never carries into the next item.
- **A video in `sounds/` goes behind the card as well as under it.** The card is then drawn from its see-through picture (`-clear.png`, saved by the card maker next to the ordinary one) over the video. Keep the ordinary picture path as it is; a card with no see-through picture fails at plan time with a message to save its match again. The video is brought to 30 fps first in the graph like every other source, its last frame is held when the card outlasts it, and its sound is never looped. A video beats a sound file of the same name.
- **"Automatic" prefers the owner's file**: a file in `sounds/` named `intro`, `goal`, `red` or `fulltime` takes the built-in sound's place for that kind of card (`automaticSounds`).
- **A sound file is named, never given as a path**, like videos: a plain file name in `sounds/` with a sound file's ending. Its format is stated in the filter chain before it is used, because a file may not say how its channels are laid out.
- **A video with a second video beside it is still one segment, as long as the first video.** The screen is split while the second runs and given to the first from the frame it ends (`besideArgs` in `src/compilation/build.js`). The first video's sound keeps its level throughout: the second's is added with `amix` set not to scale its inputs. An item with no second video must be planned and made exactly as before, so its existing segments stay valid; the second video's details go into the recipe only when there is one.
- **The Combine page's preview and the combined video come from the same sums.** `src/combine/layout.js` works out the length, how long the screen is split, how it is shared between the two (the main video has 50, 60 or 70 percent) and which part of each video shows; `Combiner.vue` draws the preview from it and `src/combine/build.js` builds the ffmpeg graph from it. Keep that file free of Node imports, and put any new setting's arithmetic there, not in the page. Both videos start together at the beginning of the result; the page lines them up by moving each one's start.
- **In the preview the main video is the clock.** The page reads its position each frame and pulls the other video back when it drifts more than 0.15 s. Both videos are stopped when the page goes away. The sound balance in the preview is only rough, and the page says so.
- **A combined video is named by its combination's id**, in the folder `combined`, and is offered to compilations only once it has been made. `made-from.json` beside it holds the settings it was made from, which is how the page marks one whose settings have changed since. It is encoded once here (`veryfast`, CRF 14) and again by the compilation; change those settings only with a new measurement (see `docs/decisions.md`).
- **Every segment of a compilation has the same settings and an explicit length**, which is what lets them be joined without encoding again. A change to the segment settings in `src/compilation/build.js` must also change `RECIPE`, or old segments would be reused.
- **A segment is reused only when everything that went into it is unchanged.** Its file name is a hash of those things, and it is written under a partial name first.
- **Paths handed to ffmpeg from `build.js` are absolute**, because ffmpeg runs inside the work folder. `list.txt` holds only names the tool made, never one a person typed.
- **`fetch` is the one way video comes in from outside, and it stays narrow.** (The other things taken from outside are facts about the channels in the sources list: a picture, a subscriber count, whether it is live. Each has its own rule below.) It takes YouTube links to a single video, a time range or the whole video, each of at most 3 hours (`MAX_FETCH_SECONDS`, `MAX_WHOLE_SECONDS`; the owner asked for whole videos on 2026-11-21, saying a video is deleted once it is clipped, and the same day for ranges longer than the old 20 minutes), and only from a channel whose entry in the sources list is marked `agreed`. The channel is read from the video's own data, not from anything typed. Do not widen any of these, add other sites, or add a way around the sources list, without the owner asking for exactly that. Since 2026-11-20 the Sources page shows no status: the owner adds a channel only once it has agreed, on their word, and every entry added is saved as `agreed`. The check in the engine is unchanged.
- **Channel pictures are taken from outside for channels in the list only, at the owner's request on 2026-11-20.** `src/pictures.js` fetches the profile picture of a channel only if it is in the saved sources list and marked `agreed`, and only after the channel YouTube reports for that address passes the same test as a video's channel (`agreedSourceOf`). The picture is the thumbnail named `avatar_uncropped`, its address must be `https` on one of YouTube's two picture hosts (`checkPictureUrl`), redirects are refused, and what comes back is decoded by ffmpeg and drawn again as a round 256-pixel PNG; the bytes that came are deleted. Nothing but those PNGs is kept, apart from one number: the same answer gives the channel's subscriber count, which the owner asked to see on 2026-11-20, and it is stored with the time it was read in `data/source-subscribers.json` (never in `sources.json`, which is the owner's record). Pictures and counts are removed with their channel, and the request to fetch them names no channel: the server uses the saved list. Do not fetch any other picture (banners, video thumbnails, anyone not in the list), and this does not lift the rule against fetching club crests.
- **Which channels are live is asked of YouTube, for channels in the saved list only** (`src/live.js`, at the owner's request on 2026-11-20). One question per channel, to its `/live` address, with nothing downloaded; the stream must pass the same channel test as a video, and its id must be a video id, before a link is built from it. The title is outside text and is trimmed to one plain line. The answer is kept in the server's memory, not on disk, and is not a job, so it never waits behind a cut. The page store `web/src/live.js` asks when the dashboard opens and at most every five minutes while its tab is on screen; do not make it ask more often, or while the tab is hidden.
- **What the owner marks on a page is saved the moment it is made, by an action that changes one thing.** On 2026-11-20 the owner lost half an hour of work: clubs marked on 55 channels waited for "Save the list", and a reload threw them away. Since then a club choice and a removal go to their own server actions (`setSourceClubs`, `removeSource` in `src/sources.js`), which read the list on disk, change the one channel and write it back, so a page showing an older copy cannot write that copy over the rest. If such a save fails, the row goes back to what is saved and says so. Do not add anything the owner picks or marks that waits for a Save button. The only things on the Sources page that still wait are typed boxes (a name, an address), and the page makes the browser ask before a reload or a closed tab would lose them.
- **Never tell the owner to reload a page that may hold unsaved work without saying so first.** Check what the page keeps unsaved before writing "reload" in a report.
- **The owner's lists are copied before every write** (`src/backup.js`): `data/sources.json` into `data/backups/sources/` (the newest 40) and `data/clubs.json` into `data/backups/clubs/` (the newest 5, since it holds every logo). Keep both lists going through `saveSources` and `saveLibrary`, which do it; never write either file another way.
- **The owner chose what travels between machines, kind by kind, on 2026-11-20**, and `src/transfer/contents.js` is the one place that says so. Travelling: the channels list with each streamer's club, the channels' pictures and subscriber counts, the leagues and clubs with their logos, the files in `sounds/`, briefs, and (chosen on 2026-11-21) the overlay images in `overlays/`. Staying local: source videos, parts, clips, combinations, compilations, and matches with their cards. Do not add a kind to the file, or take one out, without the owner saying so; when a new kind of saved data is built, ask whether it travels. Never in the file, whatever is asked: `.env` (the key rule), `data/youtube-cookies.txt` (the YouTube sign-in) and `data/backups`.
- **A load of the owner's data never deletes and never trusts the file.** It has two steps: the file is taken into `data/.incoming` and checked, the owner is shown what is in it beside what is here and what would be replaced, and only "Load it" puts it in place. Only plain files with known names in known folders are taken (`acceptEntry`, `isSafePath`); a link, a name that leaves its folder, a file that ends early, or a list the tool's own parsers refuse stops the whole load and leaves nothing behind. What a load replaces is moved to `data/backups/before-load-<time>/`, which is never cleaned out. The three lists are written last, through `saveSources`, `replaceLibrary` and `replaceSubscribers`. A waiting file is thrown away when the dashboard starts. A download and a load are refused while a job runs.
- **The data file is a tar written and read by `src/transfer/tar.js`, not by the `tar` program or a package.** It streams from disk to the browser with no copy in between, and on the way in only that code decides what an entry may be. Keep it readable by the ordinary `tar` program; a test checks that.
- **Never try "Load my data" on the owner's real dashboard to check a change.** Use scratch folders. A download is safe to try there: it only reads.
- **Sync sends the owner's data to the owner's own private repository, and nowhere else** (asked for on 2026-11-23, after a data file did not make it to the home PC; the repository is `wlc-clipper-data` on the owner's account). What goes is what `src/transfer/contents.js` lists, and nothing is added to sync that is not in that list. The address is refused when it is the repository with the code, when GitHub answers a request made with no sign-in (the repository is public), and when GitHub cannot be asked: no answer is not "private". GitHub is reached with the machine's own SSH key; no token or password is stored.
- **Every git command for sync goes through `gitIn` in `src/sync/git.js`**, which first asks git where it is and refuses unless that is `data/.sync/repo` itself. That copy sits inside this project's folder, and without its `.git` a git command there would act on the public repository. When looking at it by hand, use `git --git-dir=data/.sync/repo/.git`, never `git -C data/.sync/repo`.
- **A round of sync starts from the last state that was fully written here** (the ref `refs/clipper/applied` in the copy), commits what this machine has, fetches, puts the two together, pushes, and only then writes to this machine's files: only what differs from the round's own snapshot, and nothing at all if anything here changed while the round ran (the round is then done again with that change in it). Both halves exist because of data loss found in review: a club marked during a round was written over, and a round cut off halfway turned "not arrived yet" into "removed here". Keep both, and their tests.
- **Sync never pushes by force, never merges a list as text, and never deletes here.** A list changed on both machines is merged record by record in `src/sync/merge.js`; a record changed on both keeps GitHub's and is named to the owner as a clash. A file replaced or removed by the other machine is moved to `data/backups/sync/`. The lists are written last, through `saveSources`, `replaceLibrary` and `replaceSubscribers`, after the tool's parsers pass; a list that fails stops the round before any file is touched.
- **In the copy kept for sync, each club logo is a file** (`data/club-logos/<hash>.png`) and the clubs list names it, because the list with the logos written in is 11 MB and would be stored again on every change. A named logo that is missing stops the round; it must never become "no logo".
- **One sync action at a time** (`alone` in `server/sync.js`): looking at an address, connecting and disconnecting rebuild or remove the copy, and a round must not run across them. Sync is not a job, but it waits while one runs.
- **A whole-list save of the channels is refused when the list changed since the page read it** (`version` in `/api/sources`, sent back as `X-List-Version`), so a page opened before a sync cannot write its older copy back and have sync spread it. The single-item actions need no such check: they read the list on disk.
- **Sync's tests use a repository in a folder and scratch machines, never the network or the owner's data.** Do not connect, disconnect or change the owner's real connection to check a change.
- **`briefs/` is tracked in this public repository and is also synced**, so a brief that arrived from the other machine shows up as an untracked file here. Stage files by name; never `git add -A`.
- **The club a streamer supports is saved with the channel, by name, the moment it is chosen** (`clubs` in `data/sources.json`). The page lets one be chosen. The saved format is still a list of up to `MAX_CLUBS` names, each once, and must stay so: lists were saved while three were allowed, and a stricter format would make such a list unreadable as a whole. The page never drops extra clubs by itself; they go only when the owner chooses one. A name and not an id, because a club that is in two leagues is two entries with one name; the page shows each name once, with a logo if any entry of that name has one. A name that is no longer in the clubs list is kept and can still be taken off. `syncSource` carries the row's clubs along, so syncing a row does not lose them.
- **The sync button on a channel's row is the owner adding that channel.** `syncSource` in `src/pictures.js` takes only the row's id, address and typed name, asks YouTube about that one address, saves the channel into the list as `agreed`, then fetches its picture by the rule above. A name the owner typed is never replaced, because credits, pictures and the names of fetched files are matched on it. A name taken from YouTube is outside text: it is made one plain line of at most 80 characters, shown in the box for the owner to change, and still goes through `filePrefix`, `cleanOverlayText` and the list's own checks wherever it is used. An address already in the list under another row is refused.
- **A credit gets a picture only when it is spelled like the channel's name** (capitals aside), and a hash of what the picture shows goes into the segment's recipe only then (not its date, so fetching the same picture again remakes nothing), so an item with no picture is planned and made exactly as before. The picture is the last input and is laid on after the name (`creditLayout` in `src/compilation/build.js` places both).
- **A credit is drawn on a plate that is fitted by measuring.** The dark plate, its pale edge, its shadow and the white ring for the picture are subtitle drawings in the same file as the name (`creditSubtitles`), so no path enters the graph. The name's width is measured by drawing it alone and reading ffmpeg's `bbox` (`measureCredit`), because a name can hold any letters and `src/captions/width.js` knows only capitals. Change the `credit-2` marker in `planVideo` when the credit's look changes, or old segments are reused.
- **A stream that is live, upcoming or only just ended is refused before anything is downloaded** (`live` in what `downloader.info` returns). On a live stream the downloader ignores the range and records as the stream happens, without end. A failed or stopped download's pieces, named by the tool, are removed.
- **A fetch reads YouTube through the relay** (`src/rangeRelay.js`), because YouTube sends an open-ended request at about playback speed and a fixed slice at full speed (11 minutes against 16 s for 20 minutes). The relay listens on `127.0.0.1` only, for the length of one fetch, serves only the stream addresses the downloader gave, follows redirects only to `https` on `googlevideo.com`, and never asks for anything but the slices ffmpeg reads: only the part asked for, and the whole video only when the whole video was asked for. ffmpeg is run with the same arguments the downloader would give it, through `run()`, so Stop works. A refused slice is asked for again (three times), and the fast way is tried twice before the downloader's own slow way is used; keep that fallback. A fall back is never silent: the step is `fetching-slow` and the result's `slow` says why, with every address taken out (`fastFailure`), since a stream address holds the owner's IP address.
- **The YouTube sign-in is a password** (`data/youtube-cookies.txt`, or `CLIPPER_YOUTUBE_COOKIES`; added at the owner's request on 2026-11-21 when YouTube refused every lookup). Only its path is handed to the downloader, as `--cookies`, on every call when the file exists. Never read, print, copy, log or commit it, never put it in "My data" (`acceptEntry` refuses it, and a test checks), and keep it at mode 600 (`cookiesArgs` sets it). Advise a spare Google account: YouTube can flag accounts used by a downloader.
- **A link handed to the downloader goes after `--`** and has been rebuilt from a checked video id, so it can never be read as an option.
- **A fetched part has nothing hidden at its start.** `removeHiddenLeadIn` in `src/fetch.js` rewrites every download so the picture and the sound both begin at zero; the picture is copied, never encoded again. Without it the sound played almost 3 s away from the picture. A download that cannot be rewritten is removed, not kept.
- **A fetched file is named by the tool**: the channel's name from the sources list, the video id that was checked in the link, and the range. Nothing the downloader reports goes into a file name.
- **Running `npm run setup` again must not change the transcriber.** It updates `yt-dlp` only; faster-whisper stays at the version the captions were tested with.
- **Guardrails from the spec:** local files only apart from `fetch` and what is looked up about the channels in the sources list (picture, subscriber count, whether live); no uploading or posting (the owner's own data going to the owner's own private repository, by the sync rules above, is the one thing sent out); no feature whose purpose is removing watermarks or logos. `--trim` is capped at 5% of the shorter side for that reason.

## Adding a flag to `cut`

1. Define it in `src/cli.js` and pass it to `cut()`. For the dashboard, add it to `cutRequest` in `server/app.js` and to the form in `web/src/components/NewClip.vue`.
2. Add the parameter to `cut()` in `src/cut.js`.
3. If it changes the render: add it to the `meta` object, to the `Meta` type in `src/types.js`, and give it a default in `readMeta` so older clip folders still render.
4. Add a test, and a row in the options table in `README.md`.
5. If it departs from the spec, add an entry to `docs/decisions.md` with the reason.

## How to work here

- **Plain JavaScript.** The owner is a JavaScript developer and wants to read and change this code. Keep ES modules with JSDoc types: no TypeScript, and no second language beyond the small Python transcriber script. `src/` and `server/` run as they are, with no build step. Only `web/` is built, by Vite. The pages are plain Vue single-file components with no UI library, router or store.
- **Run the whole test suite only before a commit or push. This is the owner's firm rule.** `npm test` takes about a minute and the owner does not want it run after every change. While working on a change, run only the tests that cover it, by file or by name:

  ```bash
  npx vitest run test/compilation.test.js            # one file
  npx vitest run test/cards.test.js -t "intro card"  # tests whose name matches
  ```

  The full `npm test` is run once, as part of "Before every push" below, and it must pass there. Do not run it at any other time unless the owner asks.
- **Add a test for each new rule or flag**, in the file that covers that part of the code.
- **Measure ffmpeg behaviour, do not assume it.** `test/cut.test.js` generates a source with a white flash and a beep at a known time; use it to prove timing, sync and silence.
- **Open the dashboard in a browser after changing it.** Nothing tests the pages; `test/server.test.js` covers only the server. A page that builds is not a page that works: drive one cut and one caption fix, and read the browser console.
- **Look at the picture.** The tests do not cover where text lands on screen. To check, save a frame and open it:

  ```bash
  ffmpeg -ss 1 -i out/clip-001/clip.mp4 -frames:v 1 frame.png
  ```

- **Ask before installing or downloading anything** beyond `npm install`: system packages, pip packages, speech models, global npm changes such as `npm link`. Wait for a clear yes, and do not look for another route if a step is refused.
- **Ask before anything that sends data out**, such as the planned `suggest` command, which sends transcripts to an LLM service.
- **Do not commit or push unless asked.** When asked, follow "Before every push" below.
- **Say what was verified and what was not.** A passing test suite does not show that a clip looks or sounds right.
- **Write for the owner in plain language**, with commands ready to copy, including the `cd` into the project folder.

## Before every push

This is the owner's standing rule: the README and the knowledge files are brought up to date before anything is pushed, every time. A push that leaves them describing the old behaviour is not finished.

Go through each file against what changed since the last push (`git diff origin/main` shows it), and edit what is no longer true:

1. `README.md`: commands, flags, the brief fields, how to start things, what a clip folder contains.
2. `CLAUDE.md`: the description at the top, the commands, how the code is put together, the rules, and the checklists.
3. `docs/decisions.md`: an entry for each new choice that is not obvious from the code, with the reason and what was measured.
4. `docs/roadmap.md`: what is built, what is waiting on the owner, what is not verified, what comes next, and the "Last updated" date.

Read the whole of each file, not only the section you expect to change: a new feature usually makes a sentence somewhere else false. Then run `npm test`, and say in the report which of the four files changed and which needed nothing.

The repository is public, so before committing look through what is staged for keys: `git diff --cached | grep -nE 'sk-[A-Za-z0-9_-]{12}|API_KEY=.'` must find nothing but placeholder text, and `git check-ignore .env` must succeed.
